# ADR 001 — one-host L2 adapter, exclusive setup mode

Accepted for the first implementation; end-to-end hardware compatibility pending.

The Pi's NCM interface adopts the dongle station MAC advertised in USB descriptors. USB Ethernet frames go directly to `esp_wifi_internal_tx`; station RX goes through eight fixed copied frames and a USB worker. This is a **single-host MAC-sharing forwarder**, not a general multi-MAC Ethernet bridge. Hosts using a different source MAC are rejected. Untagged frames up to 1514 bytes are supported. IPv4, ARP, DHCP, IPv6 and multicast are passed without NAT; reflected station-source frames are discarded to avoid false ACD/DAD conflicts. VLAN trunking and arbitrary downstream bridged MACs are unsupported. TeslaAndroid must continue routing its client network as it already does.

Normal mode creates no station `esp_netif`, assigns no dongle IP, offers no DHCP server and performs no Internet probes. Successful association is not DHCP success; observed IP addresses are passive source observations, expire after 60 seconds and clear on Wi-Fi changes/USB reset. Internet state is always `not checked`. USB enumeration/transport readiness is not host-interface configuration readiness. No DHCP ACK indicator is claimed.

TinyUSB's NCM notification follows association, on its own task via deferred work. The initial link defaults down. Setup and AP loss report down; host physical unplug resets USB independently. Station MAC and serial number derive from eFuse MAC. The default Espressif development VID/PID is for prototypes; obtain suitable identifiers before distributing a product. Composite CDC-ACM is default; a network-only diagnostic artifact changes only the management class. ECM/RNDIS or NAT is a future decision only after a captured compatibility failure, not a hidden fallback.

## Setup transition

```
first boot / explicit menu or console setup
    -> restart -> setup AP + DHCP + HTTP, NCM link down
    -> save valid candidate in separate NVS key -> restart -> candidate trial
         -> associated continuously 10s within 45s -> commit candidate profile
         -> failure/timeout -> restore saved profiles, retain error
    -> cancel / 10-minute timeout -> restart -> saved adapter configuration
```

Setup flag is one-shot RTC state, honored only on a software restart. Cancel/timeout suppresses automatic first-boot setup for that restart; with no credentials the adapter remains unconfigured until a physical menu/console request or next cold boot. A failed first profile likewise requires setup re-entry. An interrupted candidate trial cannot overwrite the original profile: the candidate is consumed from NVS before applying it. Validation is **association**, not successful routing or Internet access. On commit failure the old configuration is restored. Ordinary AP failure never erases NVS or starts a provisioning AP.

Portal credentials are per-entry random 16-character temporary secrets, shown only on the physical screen. WPA2 AP, maximum two clients, ten-minute lifetime. HTTP accepts at most 400-byte JSON requests, a per-session header token, no cross-origin permission, no cache, and bounded sockets/timeouts. It is available only on the AP netif. Saved upstream passwords are never returned to browsers or diagnostics. There is no HTTPS: any holder of the temporary AP password is trusted to administer the adapter. Plain NVS is **not encrypted**; physical flash access can reveal credentials. Flash encryption/secure boot are not enabled by this prototype.

## Concurrency and memory

Network callbacks do no drawing, flash writes, dynamic packet allocation, or verbose packet logging. The Wi-Fi callback copies at most 1514 bytes into a preallocated slot and immediately frees the driver buffer. USB worker owns a slot until send-copy completion, or releases it once on rejection/cancellation. The vendored send wrapper fixes a timeout/copy double-free race; deterministic scheduler tests compile its actual body. Frames carry a network/USB epoch so queued old-subnet frames are discarded after changes.

A port spinlock protects 64-bit counters, address observations and coherent snapshots on dual-core Xtensa. Rates use byte deltas and monotonic microseconds (8 bytes/µs = 8 Mb/s); decimal MB and Mb/s. Counters are accepted-forwarding bytes, not USB wire overhead or proof of remote receipt. UI uses 32 bounded samples at four updates/second. Long text is clipped in both formatter and fixed LVGL object bounds.

Control task serializes scans, profile changes, NVS commits and trials. CDC RX only queues bounded lines; overflow rejects the entire command. Output uses a bounded queue and separate writer. No password echo. UI task priority 1 owns all LVGL calls, drawing only changed labels/graph geometry. A 5120-byte LVGL render buffer is copied to a separate 5120-byte DMA buffer; transfer completion arrives through a semaphore. If SPI stalls, the DMA buffer is retained and never reused; display rendering stops while button/network tasks continue. There is no PSRAM or microSD dependency.

IDF task watchdog watches control (10 seconds) and configured idle tasks, with panic/reboot. UI yields every 10 ms; optional UI allocation failure does not abort the bridge. RTC crash counters survive supported warm resets, clear after power-on/brownout, and snapshot packet counters once/second. Rate/history/event log and addresses are RAM-only; no payloads or secrets in the bounded 24-entry event log. Event codes: 1 associated, 2 disconnected (reason), 3 USB attach/detach, 4 trial committed, 5 trial rejected, 9 control notice/error. NVS persists only explicit configuration changes and trial staging/commit; ordinary telemetry never writes flash.
